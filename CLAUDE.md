# datainfra

A code-generation library for repository data access. Declare entities and the
operations they support in Go; the generator emits repository
implementations (currently for gorm — gocql and elasticsearch flavors live
in the sibling `datainfra-gocql` repo) plus a thin runtime layer that
plugs the generated code into a database driver.

## Repo layout

```
genlib/           # build-time code generation
  data/
    data.go       # shared handler registry + Types/Crud/Search/Associate/FilterKeys/ListByAssociatedKey markers
    types.go      # data.Entry, JenHelper, Key (key-field reflection)
    wiring.go     # data.Wiring abstraction + data.FXWiring impl (cross-flavor)
    gorm/
      gorm.go     # gorm flavor handlers (DirectoryMain, FileMain, marker types, addBaseHandlers ... addListByAssociatedKeyHandlers)
      types.go    # gorm-specific JenHelper extension (TablePrefix, TableName, ContextScopeCode)
      impl.go     # gorm.Implementation marker
pkg/              # runtime types imported by generated code
  data/
    types.go      # CrudTemplate, SearchTemplate, ListParams, PageParams, SearchPredicateDescriptor
    scopes.go     # ScopeTemplate, RootInfo
    gorm/
      gorm.go     # GetDB, WithDB, NewContextBuilder, NewDB, ErrDBNotInContext
      template.go         # MappingTemplate, DoFind, DoList (cursor pagination)
      crud_template.go    # CrudTemplate impl (Find/List/Create/Update/Delete/ExistsByKey)
      search_template.go  # PredicateBinder + Postgres/Like/Dialect binders, SearchPredicateBinding
      association_template.go, filter_keys_template.go
  data/testing/   # DoTestCrud, DoTestSearch, DoTestFilterKeys harnesses
examples/data/    # end-to-end example
  model/          # plain Go entities (Product, Category, Location, Theme)
  gen/main.go     # generator entry point (go:generate target)
  repository/     # generated types.go (shared) + gorm/ subdir (per-flavor)
```

## Generation flow

1. `examples/data/gen/main.go` builds an `[]data.Entry` describing each
   entity and its declared operations (`data.Crud`, `data.Search`,
   `data.Associate`, `data.FilterKeys`, `data.ListByAssociatedKey`), then
   layers per-flavor markers on top (e.g. `gorm.Search{Bindings:...}`,
   `gorm.Implementation{TableName: "..."}`).
2. `data.NewDataRegistry().RunFilePathHandler("../repository/types.go", ...)`
   emits the flavor-agnostic repository interfaces (`*Repository` types,
   method sets per declared operation).
3. `gorm.NewDataRegistry().RunDirectoryPathHandler("../repository/gorm", ...)`
   emits the gorm-specific implementations: one `<entity>_gen.go` per entry
   plus an optional `index_gen.go` driven by `Wiring`.
4. Both stages run from `go generate ./examples/data/...` (the `//go:generate
   go run .` directive in `gen/main.go`).

All generated files carry a `// Code generated by github.com/activatedio/gen.
DO NOT EDIT.` header — `golangci-lint`'s `generated: lax` setting recognizes
them automatically.

## Handler registry

The shared `gen.Registry` (`github.com/activatedio/gen`) dispatches builds
between three handler kinds:

- **Directory handlers** (`AddDirectoryHandler`) own a target directory and
  decide which files to emit. The gorm flavor has exactly one, keyed on
  `*DirectoryMain` — it walks `Entries`, opens a `<entity>_gen.go` per
  entry, and conditionally opens `index_gen.go`.
- **File handlers** (`AddFileHandler`) populate a single `*jen.File`. The
  gorm flavor's main file handler is keyed on `*FileMain` and is the
  workhorse — it composes the internal struct, the implementation struct,
  the params struct, and the constructor by **delegating to statement
  handlers** for each section.
- **Statement handlers** (`AddStatementHandler`) build a slice of `jen.Code`
  for one marker type. Multiple statement handlers can target the same
  marker; their outputs concatenate. This is how `data.Crud`,
  `data.Search`, `data.Associate`, `data.FilterKeys`, and any custom
  extension can each contribute fields, ctor params, and field assignments
  to the same generated struct without coordinating.

### Marker types (gorm flavor)

The internal/impl/ctor scaffolding revolves around these marker types in
`genlib/data/gorm/gorm.go`. Statement handlers register against the ones
they care about; the file handler runs them all in a deterministic order:

| Marker                     | Contributed to                                  |
| -------------------------- | ----------------------------------------------- |
| `InternalSuperFields`      | fields of `<Entity>Internal` (embeds `*Entity`) |
| `InternalFields`           | extra fields of `<Entity>Internal`              |
| `InternalFunctions`        | methods on `<Entity>Internal`                   |
| `ImplFields`               | fields of `<entity>RepositoryImpl`              |
| `ImplFieldAssignments`     | field initializers in the ctor's return literal |
| `CtorParamsFields`         | fields of `<Entity>RepositoryParams` struct     |
| `Ctor`                     | local `template :=` setup statements in the ctor body |
| `TemplateFields`           | future: shared template fields                   |
| `CrudTemplateParamsField`  | extra fields on `CrudTemplateImplOptions{...}`  |

Adding a new operation family (the apiinfra/gen escape-hatch pattern):
write an implementation marker plus a set of statement handlers that
target the markers above, then merge those handlers in via
`Registry.WithHandlerEntries(gen.NewHandlerEntries().Add...)`. The example
does exactly this for the Theme entity's `SetTenantID` method.

## Wiring (DI framework integration)

`data.Wiring` (in `genlib/data/wiring.go`) decouples generated constructors
from any specific DI framework. It exposes two hooks:

- `PrependCtorParamsFields() []jen.Code` — fields prepended to each
  `<Entity>RepositoryParams` struct (e.g. an embedded `fx.In`).
- `EmitIndex(f *jen.File, provideRefs []jen.Code)` — writes an `Index()`
  function (or equivalent) that registers the supplied constructor list.

`data.FXWiring(moduleName)` ships as the one implementation and produces
`fx.Module(name, fx.Provide(...))`. The gorm flavor's directory handler
builds the constructor list (per-flavor seeds like `gorm.NewDB`,
`gorm.NewContextBuilder`, plus every generated `New<Entity>Repository`)
and hands it to `Wiring.EmitIndex`.

Setting `Wiring: nil` on `gorm.DirectoryMain` emits plain Go constructors
with no fx import and skips `index_gen.go` entirely.

When the gocql / elasticsearch flavors in `datainfra-gocql` adopt
`data.Wiring` (planned follow-up), each will plug in its own per-flavor
seed providers (e.g. `gocql.NewClusterConfig`, `elasticsearch.NewTypedClient`).

## Search bindings

Each gorm `Search` registration carries a `SearchBinding` per supported
predicate. The binding pairs a `SearchPredicateDescriptor` (Name, Label,
Operators, Virtual) with a `Binder jen.Code` value that constructs a
`PredicateBinder` at runtime.

Convention: virtual predicates (those that don't correspond to a real
domain field — typically full-text or composite-search constructs) carry
`Virtual: true` and conventionally use a leading `@` in their `Name`
(e.g. `@keywords`). The bool is the programmatic source of truth; the
`@` prefix is the wire-visible cue for clients that consume the
descriptor list.

Built-in binders (`pkg/data/gorm/search_template.go`):

- `PostgresKeywordsBinder(column)` — `column @@ plainto_tsquery('english', ?)`
- `LikeBinder(column)` — `LOWER(column) LIKE LOWER('%v%')`; portable
- `DialectBinder(map[string]PredicateBinder)` — dispatches on
  `gorm.DB.Name()` so one registration can serve Postgres + SQLite

The generator's jen helpers (`PostgresKeywordsBinderCall`, etc.) produce
the wrapped jen code. `Search` runs every supplied criterion through its
binding (AND-chained); an unknown predicate name returns
`ErrUnknownSearchPredicate`.

## Pagination

Every list is a page. `DoList` never returns more than one page, and a
caller that wants the whole result follows `NextPageToken` — or lets
`data.Collect` do it under a ceiling.

- A nil `ListParams.PageParams`, or a `Count <= 0`, means the first page of
  `DefaultPageSize` (100) rows. `NextPageToken` is set whenever more rows
  remain, so an empty `ListParams{}` is *not* "everything"; it is page one.
- Pagination runs a forward cursor over the entity's `KeyColumns` (one for
  single keys, several for composite keys), ordered ascending, with the
  token decoded as a strict lower bound `(cols) > (vals)`. `DoList` fetches
  `Count + 1` rows, truncates to `Count`, and emits the last row's key as
  the token. Tokens are opaque to clients. The generator emits
  `KeyColumns`/`KeyAccessor` for every keyed entity.
- A template **without** key columns cannot hand out tokens. It still fetches
  `Count + 1`; if the extra row materializes `DoList` returns
  `gorm.UnpagedOverflowError` rather than a silently truncated list, and it
  rejects any `PageToken`. Configure the key columns or narrow the criteria.
- `ListParams.Selector` is applied to the fetched page in Go, so a page can
  hold fewer than `Count` rows (even none) while a token is still present.
  Terminate on the token, never on the row count.

Helpers in `pkg/data/collect.go`, both taking a `data.ListFunc[E]` (any
`ListAll`/`ListBy*` method value fits):

- `data.Collect(ctx, repo.ListAll, data.CollectParams{Max, PageSize,
  Selector})` follows tokens to exhaustion into one slice. `Max` is the
  caller's memory ceiling, default `DefaultCollectMax` (10 000); past it
  Collect returns `data.CollectLimitExceeded` (naming the ceiling, how far
  it got, and that `Max` is the lever) and **no partial result**. Rows held
  never exceed `Max` plus one page.
- `data.ExistsAny(ctx, repo.ListAll, selector)` answers "is there at least
  one row here?" under the ambient context scope without collecting. Use it
  for emptiness guards over populations that may legitimately exceed the
  ceiling; with no selector it costs a single `LIMIT 2` query. Its answer
  always agrees with whether `Collect` over the same list would be empty.

There is deliberately no count primitive: a total that ignores the label
selector answers a narrower question than the caller asked, which is the
same defect class as an unpaged read. A scoped count would have to take
the selector; none is needed yet.

## Working in this repo

```sh
# Regenerate the example (also runs the gorm pipeline):
( cd examples/data/gen && go run . )

# Test (requires Postgres on localhost:5432 with postgres/supersecret):
docker compose up -d
go test ./...

# Format + lint:
make fmt
golangci-lint run --timeout 2m
```

- After changing anything in `genlib/data/` or `genlib/data/gorm/`, rerun
  the generator and verify the diff in `examples/data/repository/`. The
  example acts as the golden output.
- After changing anything in `pkg/data/gorm/`, the existing example tests
  exercise both Postgres and SQLite. Adding a new method to the example
  generator means adding a stub elsewhere in `pkg/data/gorm/` or updating
  the example test scaffolding.
- The downstream consumer is `gitlab.authwise.io/authwise/kit`; wire-visible
  API changes need coordinated regeneration there.

## Style

- Generator code panics via `genlib.Check` / `panic(...)` for build-time
  errors — fine in `genlib/`, not in `pkg/`.
- Runtime code in `pkg/` returns errors, never panics (see
  `gorm.ErrDBNotInContext`).
- Public types carry godoc comments; package-level docs live in `doc.go`.
- The library has no other in-tree consumer than the example; treat the
  generated example output as the contract for downstream consumers.
